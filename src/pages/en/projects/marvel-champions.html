Real-time Marvel Champions events

A platform for running in-person games of Marvel Champions’ Epic Multiplayer mode. Each table keeps playing with physical cards, while the web app coordinates in real time what they all share: the villain’s health, the main scheme’s threat, the timer and cross-table cards.

Problem

In an epic Marvel Champions event, many tables play at once against the same villain. Each table deals damage, adds threat and triggers cards that affect other tables, and someone has to keep the global count without stopping play.

It needed shared state that updates instantly on every screen, a desktop interface for the organiser and a mobile one for each table, and a way to correct mistakes without losing the history.

Approach

Clients · Vue 3

Portalorganise or join Organiserdesktop: events, nodes, tables Playermobile: event code, progress

Backend · Spring Boot

REST APIJWT auth, configuration, actions WebSocketSTOMP/SockJS: broadcasts new state Action logcorrections and statistics

Data and deployment

File-based H2events, users, actions Docker ComposeNginx + backend + volume
  • REST to write, WebSocket to notify. Tables send damage, threat or cards through the API. Once the change is processed, the backend publishes the new state over WebSocket and every screen updates without reloading.
  • Three apps, one address. Portal, organiser and player are separate Vue apps, each tailored to its device, served under the same URL without duplicating shared logic.
  • Everything is logged. Each action is stored with its source table and who made it. The organiser can correct a value without erasing history, and end-of-game statistics are built from that log.
  • Delegation. The organiser assigns tables to nodes and can delegate the villain’s health, the threat or the timer to co-organisers.

Results

Measured with a purpose-built load harness: synthetic clients that log in over HTTP, subscribe over WebSocket/STOMP and write during 30 s of steady load, with 100 clients connected at once.

 “Propagation” is the time until a change reaches every client. Source: load-tests/.

The non-functional requirement was an HTTP p95 below 500 ms: it is met by a wide margin. The thesis was graded 9.7/10.

Limits

  • Local tests. They ran without network latency; a real deployment will show somewhat higher times.
  • Built for one event. File-based H2 makes deploying a single event with Docker very simple. For many concurrent events I would move to PostgreSQL.
